# Stowage Provider

The OpenTofu provider for [Stowage](https://github.com/norvexlabs/stowage). It reads only the
installer's machine interface ([guide](guides/machine-interface.md)) and decides nothing the
installer does not decide. Not in a registry yet: [install it locally](guides/install-without-registry.md).

## Example Usage

```terraform
terraform {
  required_version = ">= 1.11.0"
  required_providers {
    stowage = {
      source = "registry.opentofu.org/norvexlabs/stowage"
    }
  }
}

# The pull account fetches the installer image on the target; left out, the target's own
# `docker login` does.
provider "stowage" {
  username = "pull"
  password = var.pull_password
}

variable "pull_password" {
  type      = string
  sensitive = true
}
```

### Optional

- `kubernetes` (Block, Optional) The cluster `stowage_kubernetes_install` (and its data source) reach, named as the helm provider's `kubernetes` block. With `host`, a kubeconfig of these values is written for each run (0600, in a private directory removed afterwards); with `config_path`, that file is used; with neither, or without this block, kubectl's default (`KUBECONFIG`, else `~/.kube/config`). A provider's configuration is read at every run and never written to state. (see [below for nested schema](#nestedblock--kubernetes))
- `password` (String, Sensitive) The pull account's password or token, with `username`. Sent to the target on standard input only.
- `public_keys` (List of String) PEM public keys (`-----BEGIN PUBLIC KEY-----`, the keys a project signs its releases with, e.g. `file("release.pub")`) every installer the provider fetches must be signed by one of: a sigstore bundle referring to the installer image's digest, as `cosign sign --key` writes it, checked with no transparency log — on this machine (the Kubernetes runs, `stowage_vm_seed`), and for a Docker target before the target pulls it (every platform's image of the index). The release must then carry keys of its own (a release of a project that does not sign is refused). Left out, a first install trusts the installer's digest alone (a plan warning says so); an upgrade over an install is checked against the keys the release installed carries whatever this holds, and by the digest alone when that release carries none and this is left out. See the guide Trust.
- `registry` (String) A mirror's prefix the install pulls from instead of the project's registry (the installer's `--registry`). First-install only: a later change is a plan-time error.
- `registry_ca` (String) PEM of the certificate authority the mirror's certificate chains to (the installer's `--registry-ca`), sent on standard input.
- `registry_password` (String, Sensitive) The mirror's password or token, with `registry_username`. Sent on standard input only.
- `registry_username` (String) The mirror's own login, with `registry_password`, for the host of `registry` alone: every run on the machine running OpenTofu or a Docker target that reads the mirror (a Docker target's installer, the Kubernetes runs, `stowage_vm_seed`'s) gets it in a Docker configuration of its own, removed afterwards, the password on standard input. Needs `registry`. Left out, the mirror is read with the machine's own Docker login (`username` is the installer registry's, never sent to another host). A VM reads the mirror by itself, with what its seed gave it.
- `username` (String) The registry's pull account, with `password`: the target logs in with it, in a Docker configuration of its own removed afterwards, to fetch the installer image. Left out, the target's own `docker login` (or none) fetches it.

## Details

| Attribute | | |
|---|---|---|
| `username` | optional | The installer registry's pull account, with `password`. On a Docker target, the target logs in with it to fetch the installer image (`docker run`), in a Docker configuration of its own (`DOCKER_CONFIG` in a private temporary directory) that is removed afterwards: the credential is not left on the host. The login is written as that configuration's own `auths` entry (never by `docker login`, whose platform credential helper — a keychain — would keep it), under the key the Docker client looks the host up by (Docker Hub's `https://index.docker.io/v1/` for `docker.io` and `index.docker.io`; any other host, `registry-1.docker.io` included, its own name), the password read from standard input (a missing or empty one, or no `base64` on the machine, stops the run before anything else); the host must be a registry host (a name or address, an optional port), else refused. That configuration keeps the Docker context in use (its name, and the contexts of the configuration it replaces, linked): the login changes where the client reads credentials, never which daemon it talks to. `stowage_vm_seed`, the Kubernetes runs and the Kubernetes data source read the installer image themselves, with no Docker (its entry for the machine's platform, checked as [trust](guides/trust.md) says: [the Kubernetes target](guides/kubernetes-target.md)), logged in with it to that host. Left out, the target's own `docker login` (on this machine, the Docker configuration's `auths` and credential helpers; else none) reads it. The login goes only to the registry host of an installer the configuration names (the resource's `installer`, or the one state records; `docker.io` for a reference without a host) or of the provider's `registry`: a reference read back from a target or a release that names another host (`status --json`'s installers) is read with the machine's own Docker configuration, else anonymously. |
| `public_keys` | optional list | PEM public keys every installer the provider fetches must be signed by one of; refused unless each is a PEM public key (`public_keys[i] is not a PEM public key`). Left out, a first install trusts the installer's digest alone (a plan warning); an upgrade is checked against the keys the release installed carries either way, and by the digest alone when that release carries none. [Trust](guides/trust.md). |
| `password` | optional, sensitive | The pull account's password or token, with `username`; sent on the target's standard input only. One without the other is refused. |
| `registry` | optional | A mirror's prefix (the installer's `--registry`), given at the install; a trailing `/` is taken off, as the installer records it. First-install only: the resource records it (`registry`), and a plan whose provider `registry` differs, as written, is an error (left out means the release's own registry, which a plan cannot read: naming it over an install made without a mirror is a change too — leave it out). |
| `registry_ca` | optional | PEM of the mirror's certificate authority (the installer's `--registry-ca`), sent on standard input. Refused unless it holds `-----BEGIN CERTIFICATE-----`. A Docker target's daemon must already trust the mirror to fetch the installer image itself; the provider's own reads of the installer image (`stowage_vm_seed`, Kubernetes) trust it besides the system's CAs. |
| `registry_username`, `registry_password` | optional, the password sensitive | The mirror's own login, for the host of `registry` alone (both or neither; refused without `registry`). Every run that reads the mirror gets it in its Docker configuration of its own (the `auths` entry beside any other, removed afterwards), the password on standard input as `mirror-password` in the run's tar, never a flag or an argument: a Docker target's installer runs (install, re-run, upgrade, rollback, status, uninstall), every Kubernetes run, `stowage_vm_seed`'s run, and an installer image's fetch from that host. `image_pull_login` writes the cluster's pull Secret from it. Left out, the mirror is read with the machine's (or target's) own Docker login. `username` stays the installer registry's: it is never sent to the mirror's host. A VM reads the mirror by itself, with what its seed gave it: `stowage_vm_install`'s `registry_login_wo` gives a VM its own. |
| `kubernetes` | block | The cluster the Kubernetes targets reach, below. |

On Kubernetes, `registry` is the installer's `--image-registry`: the chart and the images come from
the mirror, for which the installer writes no pull Secret. The cluster's nodes must pull from it on
their own (an anonymous mirror, or the container runtime's credentials on each node): the provider
gives the chart no values file.

**`kubernetes` block** — how the cluster is reached, named as the helm provider's `kubernetes`
block. A provider's configuration is read at every run and never written to state: its
credentials are not in state, and a short-lived token (`exec`) is fetched again each run. With
`host`, a kubeconfig of these values is written for each run (one cluster, user and context named
`stowage`; PEM values as their `*-data`; 0600, in a private 0700 temporary directory removed when
the run ends); with `config_path`, that file; with neither (or no block), kubectl's default:
`KUBECONFIG` (each file made absolute), else `~/.kube/config`. A value not known yet (a cluster
made in the same apply) is checked, and used, when the apply configures the provider again; an
install run while one is still unknown is an error (`The provider's kubernetes block is not known
yet`).
