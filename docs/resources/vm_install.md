# stowage_vm_install (Resource)

The install of a Stowage product on a Kairos VM, reached over SSH: a VM its hypervisor's or cloud's resource made from `stowage_vm_seed`. `sudo -n <short_name>-stow install|upgrade|rollback --json` and `<short_name>-stow status|describe --json` run on it; destroying the resource forgets the install, removing the VM is its own resource's job.

What each operation runs on the VM: [the VM target](../guides/vm-target.md); a whole root per platform: the [platform guides](../guides/platforms.md). A destroy (with `deletion_protection` off) forgets the resource: removing the VM is its own resource's job, which a root runs after it.

## Example Usage

```terraform
# The install on a Kairos VM a hypervisor's resource made from stowage_vm_seed (a whole root per
# platform: the platform guides).
resource "stowage_vm_seed" "notes" {
  installer      = "registry.example.com/notes/notes-installer@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  platform       = "truenas"
  hostname       = "notes"
  user           = "ops"
  ssh_public_key = file(pathexpand("~/.ssh/id_ed25519.pub"))
  network        = "static"
  address        = "192.0.2.10/24"
  gateway        = "192.0.2.1"
  dns            = ["192.0.2.1"]
  tls            = "internal"
}

# ... the VM, from stowage_vm_seed.notes.user_data and .disk (see the platform guides) ...

resource "stowage_vm_install" "notes" {
  host             = "192.0.2.10"
  user             = "ops"
  private_key_file = pathexpand("~/.ssh/id_ed25519")
  known_hosts_line = stowage_vm_seed.notes.known_hosts_line # the one-time key, until the VM's own is read
  short_name       = stowage_vm_seed.notes.short_name
  version          = stowage_vm_seed.notes.version # a later release upgrades the VM
  platform         = stowage_vm_seed.notes.platform

  inputs = { ADMIN_EMAIL = "ops@example.com" }
  tls    = "internal"

  # depends_on = [<the VM's power resource>]
}
```

## Details

### Arguments

| Attribute | | |
|---|---|---|
| `inputs` | optional map | Non-secret inputs, each given as `--set KEY=VALUE`. They are on the target's command line and in state. A key is a letter or `_`, then letters, digits or `_`; `tls` is refused (the answers file's reserved section). An input given a non-empty value here that `describe` marks `secret` (its `inputs`, and the inputs a TLS mode adds, `tls_inputs`: the secret `STOWAGE_CLOUDFLARE_API_TOKEN` of `dns-cloudflare`, from Stowage 0.38.0) is refused: at create, and at an update (every key of the map, changed or not) for the running release and the one an upgrade goes to, before anything runs. A key taken out of the map is given empty (`--set KEY=`) to the re-run: the installer's rule for an empty value decides (a required input is refused, an advanced one goes back to its default); a key taken out that `secret_inputs_wo` now holds is not (`--set` would win over its answer), and, given another value than `inputs` gave, needs a new `secret_inputs_wo_version` in the same apply (else a plan error, `an input moved to secret_inputs_wo`, on every target; OpenTofu plans again with the final configuration before an apply, so an apply never sees one). A refresh reads the value the install records (`status --json --values`) for each key given and keeps it in the resource's private state: one whose record changed since the last record (the refresh before, or the end of the last create or update, which reads it too) and differs from the configuration's (a kit taken gave it, a re-run by hand) is put in state, so the next plan gives the configuration's again; a value the installer records otherwise than given (an empty one as its default) records the same each time, so it is no change; a file input is compared by its digest. |
| `secret_inputs_wo` | optional map, **write-only** | Secret inputs, never in plan or state, sent on standard input as an answers file (`--answers`). A key in both maps is refused. |
| `secret_inputs_wo_version` | optional number | Change it to apply a change of `secret_inputs_wo` (a write-only value is never compared): the update re-sends every secret input the running release declares, a TLS mode's (`STOWAGE_CLOUDFLARE_API_TOKEN`) included; without a change an upgrade sends only those the new release adds. Leaving it out with `secret_inputs_wo` set is a warning. |
| `secret_rotations` | optional map of numbers | A number per generated secret of the release (`{ SESSION_SECRET = 1 }`), as `random_password`'s `keepers`: a changed number rotates that secret in that apply, over SSH as the other verbs — `sudo -n <short>-stow secrets rotate KEY --yes --no-input` for a secret whose spec has `replace: true` (one pass: nothing of the old value kept), or its three passes `--stage`, the swap and `--finish` for one with `rotation: true`, each a job of the VM's host daemon. A key's first number — at the create, or a key added later — is recorded and rotates nothing; a key taken out is forgotten. A key the release does not rotate on this target (`describe --json` `secrets[].rotate`: `none`, or no way named for the target), or that is no generated secret of it, is refused (`KEY does not rotate on SHAPE`, `not a generated secret of the release`; a way this provider does not run: `KEY rotates in a way this provider does not run`): at the create, before the install; at plan, when the plan keeps `version` and the provider read the `describe` of the release state runs (at the create, a rotation, or, while `secret_rotations` is set, an update after which the ways kept are not the running release's — a read that fails then is a warning, `… (the release's rotate ways not read)` —, kept in the resource's private state; not after a refresh that reads another release, nor for a state made by an earlier provider or an import never applied with `secret_rotations`); else by the apply, after the update's other steps (saved) and before any rotation. A release whose `describe` lists no `secrets` (one built by Stowage before 0.46.0) takes none (`secret_rotations needs a newer release`). The keys rotate in key order, after the update's other steps, on the release the install runs then, within the update's timeout; the first that fails stops the rest, which keep their number (the next plan shows them again), and a rotation by passes resumes in the next apply at the pass that failed (`The rotation of KEY stopped at …`; running a pass again is safe: one whose change the installer recorded brings the stack up with it), the passes before not run again. A resumed pass that fails again keeps the resume point (`Rotating KEY stopped part-way`); when the target's rotation was finished or moved on by hand since, take the key out, apply, then give it back: the apply that adds it records its number and forgets where the rotation stopped, so its next rotation starts at `--stage`. A first pass refused changed nothing and leaves no resume point, and a key whose way is no longer `passes` (another release) drops its own; a stopped rotation whose number is given back to state's is a plan warning (`the rotation of KEY is not finished`). |
| `given_wo` | optional, **write-only** | What another install gives (the installer's `--given` YAML), used at create, on standard input. |

With `given_wo`, refused at validation (`kit_wo with given_wo`). |

| `deletion_protection` | default `true` | While true, a destroy is refused (`deletion_protection is on`). Set it `false` and apply first. |
| `plan_dry_run` | default `false` | On Docker, a plan changing `installer` alone (no re-run of the running release beside it) runs the change's dry run on the target, the step chosen from the install's `status --json` by the apply's own rule (its errors — `a rollback needs allow_rollback`, `installer is another digest of the release installed`, first-install settings the install holds otherwise — at plan, or the apply's alone), so the installer's refusal is a plan error (its reason the summary, its fix the detail): an upgrade's — `sh -c '…' sh <work_dir>` removes the plans' directories older than an hour there, then makes a private (0700) `<work_dir>/.stowage-plan.XXXXXX` beside the install; the new installer is fetched into it (as at create, logged in the same way) and described, the inputs checked as the apply checks them (a secret input in `inputs` refused before anything runs), then `sh ./<name>.sh upgrade --dry-run --no-input --json --dir <work_dir>/<name> [--set K=V]… [--ports]` runs in that directory (what it extracts stays there) with what the upgrade would be given (the inputs, secret inputs as `--answers` and ports the new release adds), and the directory is removed (only a `.stowage-plan.XXXXXX` of the work directory is; a removal that fails is a warning); a rollback's — the inputs checked as for the upgrade (a secret input in `inputs`, and on this machine an input the run's environment sets, refused before anything runs), then the kept installer's `rollback --dry-run --json`, without the inputs' variables as the apply's. A plan that also re-runs the running release gets a warning instead (`No dry run of this plan`: the upgrade runs on what that re-run leaves; told before anything is fetched when the change is the running release's whatever the new one is: TLS, domains, a secret input, an input it declares that the plan gives, a port of a route it has), a rollback with one is `a rollback goes alone` (as at apply, its status's `previous` deciding a rollback); an install gone since its status was read gets a warning too (the apply says what it finds); an input moved to `secret_inputs_wo` without a new version is refused before anything is fetched; one whose configuration holds a value not known yet (but `deletion_protection`, `delete_data` and `timeouts`, which no dry run reads), or with a setting a run reads not known yet (the pull account, `registry`, `registry_ca`, the mirror's login, `public_keys`), no dry run, with a warning (`No dry run of this plan yet`: OpenTofu plans again at apply, with it known, and that plan runs it); an install whose home `work_dir` was never resolved (an import's), nothing but a warning (`Taking over the install: its values are not read at plan`).  A failure is a plan error too. The fetched image stays in the daemon's store, and the dry run takes the install's lock while it reads it (an apply of the same install meanwhile is refused by it). Opt-in: the plan reaches the target, and OpenTofu plans again at apply, which runs it again. On an imported state never applied it runs too, and says what the take-over changes (`Taking over the install: …`); its rollback is refused (`a rollback of an imported install`). On Kubernetes and the VM: see their guides (the new installer's `k8s upgrade --dry-run` or `k8s rollback --dry-run`; the VM's `upgrade --version V --dry-run` or `rollback --dry-run` over SSH, Stowage 0.38.0 or later on its OS). |
| `timeouts` | block | `create` (default 30m; it bounds the wait for a first install still `installing`), `read` (5m), `update` (30m), `delete` (15m). A run cut by its timeout is a failure. |

A null value in `inputs`, `secret_inputs_wo`, `domains` or `ports` is refused by its key
(`<attribute>.<key> is null`); a value not known until apply (an ephemeral variable's, one computed
from another resource) is not, its key checked when the configuration is validated.

### Changing SSH's sources

The apply sets `ssh_allow` last — after the re-run, an upgrade's or a rollback's reboot, the NICs'
reboot, the backup settings and the rotations — over SSH, each a run of its own:

1. `sudo -n <short_name>-stow ssh-allow --json`: the sources the VM accepts. Equal to `ssh_allow`
   (as sets), nothing more runs. A change already awaiting confirmation there fails the apply
   (`a change of SSH's sources awaits confirmation on the VM`), naming `sudo <short_name>-stow
   ssh-allow confirm` (over a new SSH connection) and `ssh-allow revert`.
2. `sudo -n <short_name>-stow ssh-allow set <sources, sorted> --json`: the VM applies them at once
   and undoes them unless they are confirmed within its window (90 s). One refused because a change
   awaits confirmation names the same two verbs.
3. `sudo -n <short_name>-stow ssh-allow confirm --json`, over a **new** SSH connection (the
   provider never shares one): the VM lets it in only when the new sources hold the address
   OpenTofu runs from. When ssh cannot connect (exit 255), the apply fails naming the window that
   undoes the change by itself (its seconds, and the sources it goes back to) and the likely cause:
   `ssh_allow` leaves out the address OpenTofu runs from. A confirm that fails otherwise is
   followed by `sudo -n <short_name>-stow ssh-allow revert --json`, and the error says both.

An update that fails at any step keeps state's `ssh_allow`, so the next plan shows the change
again. At create, a failure is a warning (`SSH's sources are not set on the VM`): the install is
recorded with `ssh_allow` as planned and marked pending in the resource's private state, and the
next plan is an update that sets it (`SSH's sources not set yet`). An OS built by Stowage before
0.50.0 has no `ssh-allow` (`no ssh-allow verb`): upgrade the VM first.

A refresh reads `ssh-allow --json` while `ssh_allow` is set: sources other than state's are put in
state (drift); a change awaiting confirmation there is read as its sources, with a warning naming
when it goes back (`A change of SSH's sources awaits confirmation on the VM`); a rule file that
does not read as SSH's sources (`sources` null) leaves state's, with a warning naming why, as does
a read that fails (`Reading SSH's sources on the VM failed`).

**From one address to another.** An apply run from an address the old sources refuse cannot reach
the VM at all, and one whose new sources leave out the address it runs from has its change undone
by the window. Move in two applies: add the new address beside the old ones, apply (from the old
address, or the new one once a platform firewall lets it through), then take the old ones out and
apply from the new address. A VM no address reaches any more is reached through its platform's
console alone (`sudo <short_name>-stow ssh-allow set …` there). A platform firewall in front of the
VM — a cloud's security group the root builds from `stowage_vm_seed`'s `firewall.ssh_sources` —
does not follow `ssh_allow`: widen it in the same apply, from the same list (for example one
variable feeding both), and make the install depend on it so it opens first.

`secrets_wo` goes to the create's `install --secrets` (on standard input): for a VM seeded with
`stowage_vm_seed`'s `await_secrets`, whose first install waits for it. The create reads the VM's
`status --json` first: while a first install runs on (`installing`, not `install_failed`), it
stops (`The first install is still running`); an install a restore that was cut or failed left
half restored (`volumes_split`) is refused, naming the restore that finishes it; an install an earlier apply made from the export
(`made_again`, Stowage 0.48.0 or later, or `restore_awaited`) is not given it again (a warning)
and is run again with the configuration's settings; a first install that wrote no install yet
(`installed` null, failed or not) is given it again; an installed VM given a new install's secrets
file (no `export: true`) is refused (`The VM holds an install of its own`: if an earlier apply's
install took it, remove `secrets_wo`); any other install is refused (`The VM holds
an install of its own`), naming the way on and the restore by hand that loads its data. A re-run never gives it. The whole flow, with `backup` and `restore`: [the VM
guide](../guides/vm-target.md#a-machine-made-again).

A first boot whose reset failed in Kairos's recovery system (`status --json` `reset_failed`) fails
the create at once, naming the reason, as no later poll would answer otherwise.

### Plan-time errors

A change of a first-install-only setting — `channel`, `short_name` (the VM's installer is its
seed's, or the import ID's), the provider's `registry` and `registry_ca` — is a plan error naming
the old value, never a replacement.

A key of `secret_rotations` added or changed that the release does not rotate on this target is a plan error when the provider read the release's ways before and the plan keeps the release (see `secret_rotations`).

Also plan errors: `version` changed to `previous.version` without `allow_rollback` (`a rollback
needs allow_rollback`); `known_hosts_line` left out while `seed_boot_id` is set
(`known_hosts_line is still needed`); `tls` taken out (`tls cannot be removed`); a route taken
out of `domains` or `ports` (`domains.<route> cannot be removed`); a rollback with any other
change of what the VM applies (`a rollback goes alone`); `interfaces` changed with `version`
(`interfaces change with version`). A plan changing anything the VM applies plans `status`,
`revision` and `previous` unknown (the update reads them after its run); `seed_boot_id` unknown
while it is set, and `host_key_line` and `seed_boot_id` unknown while state has no
`host_key_line` (the update learns it). An imported state's first apply also plans `registry` and
`registry_ca_digest` unknown (it records them).
