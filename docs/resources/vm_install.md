# stowage_vm_install (Resource)

The install of a Stowage product on a Kairos VM, reached over SSH: a VM its hypervisor's or cloud's resource made from `stowage_vm_seed`. `sudo -n <short_name>-stow install|upgrade|rollback --json` and `<short_name>-stow status|describe --json` run on it; destroying the resource forgets the install, removing the VM is its own resource's job.

What each operation runs on the VM: [the VM target](../guides/vm-target.md); a whole root per platform: the [platform guides](../guides/platforms.md). A destroy (with `deletion_protection` off) forgets the resource: removing the VM is its own resource's job, which a root runs after it.

## Example Usage

```terraform
# The install on a Kairos VM a hypervisor's resource made from stowage_vm_seed (a whole root per
# platform: the platform guides).
resource "stowage_vm_seed" "notes" {
  installer      = "registry.example.com/notes/notes-installer@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  platform       = "truenas"
  hostname       = "notes"
  user           = "ops"
  ssh_public_key = file(pathexpand("~/.ssh/id_ed25519.pub"))
  network        = "static"
  address        = "192.0.2.10/24"
  gateway        = "192.0.2.1"
  dns            = ["192.0.2.1"]
  tls            = "internal"
}

# ... the VM, from stowage_vm_seed.notes.user_data and .disk (see the platform guides) ...

resource "stowage_vm_install" "notes" {
  host             = "192.0.2.10"
  user             = "ops"
  private_key_file = pathexpand("~/.ssh/id_ed25519")
  known_hosts_line = stowage_vm_seed.notes.known_hosts_line # the one-time key, until the VM's own is read
  short_name       = stowage_vm_seed.notes.short_name
  version          = stowage_vm_seed.notes.version # a later release upgrades the VM
  platform         = stowage_vm_seed.notes.platform

  inputs = { ADMIN_EMAIL = "ops@example.com" }
  tls    = "internal"

  # depends_on = [<the VM's power resource>]
}
```

While it is set, a connection also accepts `known_hosts_line`, which a plan refuses to drop (`known_hosts_line is still needed`). It goes null: at a read or an update whose status shows a later boot (which retired the key); after an upgrade's or a rollback's followed reboot; when an update's retirement, tried again, holds — an update without a release change tries it in its first steps, one with a release change whose upgrade or rollback had nothing to do (no reboot) tries it then, unless a retirement already failed earlier in the same apply. Each retry that fails is a warning (`The VM's one-time host key is still not retired`). From the moment it goes null, the update's connection accepts the VM's own key alone. |
| `platform` | optional | Where the VM runs, `stowage_vm_seed`'s `platform`. A wait of the create that runs out (the first boot, the first install) names that platform's console (`The VM's boot shows on …`: TrueNAS's display, Proxmox VE's console, `virsh console`, vSphere's console, Hyper-V Manager, the machine's screen, a cloud's serial console). A destroy's plan (before it is approved) asks the VM's installer whether the registry still holds a disk set a VM of its release boots there (`sudo -n <short_name>-stow vm seed --json --platform P --ssh-key FILE [--registry R]`, its output discarded, bounded to two minutes, its connection to 10 seconds: a VM that does not answer is not checked, a warning saying so, `Whether this VM can be made again was not checked`): none is a warning (`No disk set to make this VM again`, naming the installer's reason), a check that fails another (`Whether this VM can be made again is not known`); neither stops the destroy, whose apply asks nothing. Nothing is asked without `platform`, or before the VM's own key is known. |
| `interfaces` | optional map of objects | NICs of the release's secondary roles (`host.interfaces`) the VM's platform attached after its seed, by role: `mac` (required), `mode` (`dhcp`, `static` or `none`; left out, the installer's `none`) and `address` (IPv4 with its prefix, with `static` alone: `static` without one, or one without `static`, is refused at validation). A role added or changed — at create, once the install is done; at an update, after the re-run — runs `sudo -n <short_name>-stow network attach --role R --mac M [--mode] [--address]` over SSH for each (sorted by role), then `sudo -n <short_name>-stow reboot`, and follows the reboot to the health gate's verdict, as an upgrade's: the NICs are named from that boot. An update first waits for the VM to answer over SSH (the platform restarted it to give it the NIC), an imported state's first apply too. The platform's device comes first: the root adds it and restarts the VM (TrueNAS: `truenas_vm_power`'s `restart_triggers` keyed on the NIC devices), and this resource depends on that restart. State is saved before the attach: at an update, one that fails leaves the roles it attaches as before (an error; the other roles as planned, an imported VM's taken over among them), so the next apply attaches those again; at create, one that fails is a warning, the install recorded with `interfaces` as planned and those roles pending in the resource's private state, so the next plan is an update (`NICs not attached yet`) that attaches them. A reboot the health gate found unhealthy after the attach records the NICs attached, nothing pending, the verdict a warning at create (`The VM came back unhealthy from attaching its NICs`) and an error at an update (`Attaching the VM's NICs`): no apply attaches them again. An imported state's first apply attaches only the roles the VM does not name already (`network --json`), all of them when that cannot be read: [the VM target](../guides/vm-target.md). A role taken out runs nothing (the VM keeps its record). A change of `interfaces` with one of `version` is a plan error (`interfaces change with version`; for an imported state, an apply error). |

`secrets_wo` goes to the create's `install --secrets` (on standard input): for a VM seeded with
`stowage_vm_seed`'s `await_secrets`, whose first install waits for it; on a VM whose first install
ran, the installer refuses it, and the create fails with its reason. A re-run never gives it.

A first boot whose reset failed in Kairos's recovery system (`status --json` `reset_failed`) fails
the create at once, naming the reason, as no later poll would answer otherwise.

### Plan-time errors

A change of a first-install-only setting — `channel`, `short_name` (the VM's installer is its
seed's, or the import ID's), the provider's `registry` and `registry_ca` — is a plan error naming
the old value, never a replacement.

Also plan errors: `version` changed to `previous.version` without `allow_rollback` (`a rollback
needs allow_rollback`); `known_hosts_line` left out while `seed_boot_id` is set
(`known_hosts_line is still needed`); `tls` taken out (`tls cannot be removed`); a route taken
out of `domains` or `ports` (`domains.<route> cannot be removed`); a rollback with any other
change of what the VM applies (`a rollback goes alone`); `interfaces` changed with `version`
(`interfaces change with version`). A plan changing anything the VM applies plans `status`,
`revision` and `previous` unknown (the update reads them after its run); `seed_boot_id` unknown
while it is set, and `host_key_line` and `seed_boot_id` unknown while state has no
`host_key_line` (the update learns it). An imported state's first apply also plans `registry` and
`registry_ca_digest` unknown (it records them).
