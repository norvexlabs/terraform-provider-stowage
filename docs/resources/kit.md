# stowage_kit (Resource)

A handoff kit issued by an install (`kit create HANDOFF --json`, the request on standard input or in a private file, never on a command line), for the ephemeral `stowage_kit` to hand to what takes it in the same apply: `stowage_*_install`'s `kit_wo`, or `stowage_kit_take`'s. The kit and its code are kept in the provider's process alone: never in state, a plan, a file of the root or a log (the runs that issue and take it pass it through a private temporary directory, removed when they end). A create, or a change of `answers`, `expires` or `version`, issues a kit; a refresh runs nothing. Destroying it forgets the kit: what the handoff issued is the project's to revoke.

## Example Usage

```terraform
# A kit the install "issuer" issues for another install of the project its handoff names; the
# ephemeral stowage_kit hands it on in the same apply (see the guide Handoff kits).
resource "stowage_kit" "site_b" {
  handoff    = "second-site"
  instance   = "site-b"
  answers    = { SITE_ADMIN = "admin@b.example" }
  answers_wo = { SITE_TOKEN = var.site_token } # a secret question: write-only, never in state
  expires    = "1h"
  version    = 1 # bump to issue again

  docker {
    host             = stowage_docker_install.issuer.host
    user             = stowage_docker_install.issuer.user
    known_hosts_line = stowage_docker_install.issuer.known_hosts_line
    install_id       = stowage_docker_install.issuer.id
    short_name       = stowage_docker_install.issuer.short_name
  }
}

ephemeral "stowage_kit" "site_b" {
  id = stowage_kit.site_b.id
}

resource "stowage_docker_install" "site_b" {
  installer      = var.installer
  kit_wo         = ephemeral.stowage_kit.site_b.kit
  kit_code_wo    = ephemeral.stowage_kit.site_b.code
  kit_wo_version = stowage_kit.site_b.id
  # …
}
```

## Schema

### Required

- `handoff` (String) The handoff's name, as the issuing release's `describe --json` lists it in `handoffs`.

### Optional

> **NOTE**: [Write-only arguments](https://developer.hashicorp.com/terraform/language/resources/ephemeral#write-only-arguments) are supported in Terraform 1.11 and later.

- `answers` (Map of String) The answers to the handoff's questions that are not secret, by key (`describe` `handoffs[].ask`). A question `secret` there given here is refused before anything is issued (`A secret answer in answers`): give it in `answers_wo`, as this is in plan and state. A change issues a kit again.
- `answers_wo` (Map of String, [Write-only](https://developer.hashicorp.com/terraform/language/resources/ephemeral#write-only-arguments)) The answers to the secret questions (and any other), write-only: sent in the request at each issue, never kept. A change of it alone issues nothing: bump `version`.
- `docker` (Block, Optional) The Docker install that issues the kit: its kept installer runs on its host, as the install resource's runs do. (see [below for nested schema](#nestedblock--docker))
- `expires` (String) How long the kit is good for, a duration (`30m`, `1h`, `168h`), after now; default `1h`. The installer caps it. A change issues a kit again.
- `instance` (String) The instance the kit is issued for; left out, the handoff's name (the installer refuses that when the handoff asks the instance).
- `kubernetes` (Block, Optional) The Kubernetes release that issues the kit, on the cluster the provider's `kubernetes` block reaches (another cluster: a provider alias). The release's installer runs on the machine running OpenTofu (`<name>.sh k8s kit …`, `k8s upgrade --kit`). (see [below for nested schema](#nestedblock--kubernetes))
- `version` (Number) Bump it to issue a kit again (with `answers_wo` as the configuration holds it), e.g. after an apply that issued one failed before it was taken.

## Details

The install that issues the kit is named by one block, holding what its install resource exports:
`docker` (its SSH settings, `install_id` = the install's `id`, `short_name`), `kubernetes`
(`installer`, `namespace`, `release`: the cluster is the provider's `kubernetes` block) or `vm`
(`host`, `user`, `known_hosts_line` = `stowage_vm_install`'s `host_key_line`, `short_name`). Exactly
one is given, else a validation error (`One install, in one block`); an attribute the block needs
left out is one too (`Missing docker.install_id`, …). Changing what names the install
(`install_id`, `short_name`; `namespace`, `release`), `handoff` or `instance` replaces the resource; a
change of how it is reached alone (`host`, `port`, `user`, `private_key_file`, `known_hosts_line`, the
Kubernetes `installer`), as the install resources take a new host for the same install, is recorded
in place, nothing issued, the `id` kept.

**Create, and an update** (a change of `answers`, `expires` or `version`): the release's `describe --json` — Docker: the kept installer's
`<install_id>/<short_name>-stow describe --json`; Kubernetes: the `installer` fetched and checked as
the install resource's ([trust](../guides/trust.md)), whose release must be the one the cluster runs
(`k8s status --json`: its recorded installer, else its version and revision; another is an error,
`The release runs another installer`; none in the namespace, `No release there`); VM: `<short_name>-stow describe --json` over SSH. Its
`handoffs` must list `handoff` (else `No such handoff`, naming those it issues; a release made before
Stowage 0.44.0 lists none); a Docker `install_id` whose directory holds no install is `No install
there`. Refused then, before anything is issued: a question `ask` marks `secret`
answered in `answers`, which state holds (`A secret answer in answers`: give it in `answers_wo`), and a
handoff whose `gives` lists a `KIT_TLS_*` key (`A handoff giving TLS material`): a kit's `tls` moves its
target's front to `byo`, which the target's install resource's `tls` does not say — issue that one by
hand. Then `kit create HANDOFF --json`: Docker, the kept installer with the request as the file
`--request` reads, sent on standard input in a private directory; Kubernetes, `<name>.sh k8s kit create
HANDOFF --json --request FILE --namespace … [--release …]` with the provider's `registry_ca`; VM, `sudo
-n <short_name>-stow kit create HANDOFF --json` with the request on standard input. The request is
`{instance, answers, expires}`: `answers` and `answers_wo` merged (a key in both is a validation error),
`expires` in nanoseconds. The installer checks it (a question left unanswered, an instance the handoff
asks, an expiry past its cap: its refusal, before the run; an exit 3 says `refused before the run:
nothing was issued`). Its answer `{kit, code}` is kept in the
provider's process memory under a new random `id`, and nowhere else: never state, a plan, a log or a
file. A failure after the run may have started says so (`if the handoff's run started, what it issued
is lost`): the project's script decides whether it can be issued again; bump `version` to try.

A root orders the runs on one install: each kit resource after its install resource, by giving it
that resource's attributes (`id`, `short_name`, `installer`, `namespace`, `host`: OpenTofu then
runs it after the install's create or update), and the kit resources on one install after one
another (`depends_on`), as `examples/guides/handoff-chain` does. The provider orders nothing
itself. On Docker and the VM, the installer's own lock refuses a run while another holds the
install (`a provision, upgrade, rollback or reset-db is already running for this install: wait
for it to finish`, exit 3); on Kubernetes, helm refuses an upgrade (a take) while another is
pending, and a kit's Job runs beside anything, so an issue or a check beside the release's
upgrade is not refused.

**Refresh** runs nothing. **Destroy** forgets the kit: what the handoff issued is the project's to
revoke. **Import** is not supported.

The kit reaches what takes it through the ephemeral `stowage_kit` (same provider configuration: a
provider alias is another process, which holds nothing), into `kit_wo` and `kit_code_wo` of
`stowage_*_install` (a first install) or `stowage_kit_take` (an install that exists). In any later
plan or apply the ephemeral is null; what takes the kit sets `kit_wo_version` to this resource's
`id`, so a null kit where one is expected is an error naming the fix (bump `version`), never an
install without it. See the guide [Handoff kits](../guides/handoff-kits.md).
